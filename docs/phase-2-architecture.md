# SamarthLoan Phase 2 architecture

## Deployment decision

SamarthLoan will retain the existing React/Vite frontend and Express API. Local
development can use SQLite, while staging and production use PostgreSQL through
`DATABASE_URL`. The Express API is deployed separately from the Netlify static
site; `VITE_API_URL` identifies that API origin. Netlify must not rewrite
`/api/*` to `index.html` in production.

```text
React/Vite → HTTPS → Express API → Drizzle → PostgreSQL
                              └→ SQLite (local development only)
```

No managed database provider is assumed. The application remains unconfigured
for staging/production until `DATABASE_URL` is supplied in the deployment
secret store.

## Migration policy

1. Migrations are checked into `lib/db/migrations` and applied forward only.
2. No migration drops an existing user-owned table or column.
3. Legacy application/profile records are migrated before legacy tables are
   retired.
4. Existing catalogue and partner rows are not treated as verified data. They
   are excluded from public responses until an administrator adds a source,
   source name, and verification date.
5. Development, staging, and production each use their own database URL and
   migration run; no environment shares a database file or secret.

## Authentication decision

The repository has no authentication implementation. Phase 2 will introduce
server-managed, signed, httpOnly sessions with password hashes generated by
Node's `scrypt` API. Passwords and tokens are never stored in plaintext.
Production requires `AUTH_SECRET`, secure cookies, HTTPS, and an approved
email/phone verification provider before public account onboarding is enabled.

## Data provenance policy

Scheme and partner records are admin-managed database records. A record is
publicly discoverable only when it has a valid source URL, source name, and
last verification date. Unknown loan terms, operational metrics, and partner
authorizations remain unavailable rather than being inferred.

## Planned core relationships

```text
users ──< user_profiles
users ──< scheme_match_requests ──< scheme_match_results >── schemes
users ──< financial_calculations >── schemes
users ──< scheme_applications >── schemes
                               >── channel_partners
schemes ──< scheme_translations
schemes ──< scheme_eligibility_rules
schemes ──< partner_scheme_mappings >── channel_partners
channel_partners ──< partner_operational_metrics
users ──< support_requests, notifications, audit_logs
```

## Legacy data audit

The local database was inspected on 18 September 2026. It has no records in
`schemes`, `partners`, `applicant_profiles`, `applications`, `emi_calculations`,
or `contact_enquiries`; it has 14 legacy recommendation records. No user data
will be deleted. The recommendation records can be retained as legacy records
only after a migration creates a compatible parent request, otherwise they are
not shown in the product.
